                          MoLE HTTP Transport
                  draft-jms-mole-http-transport-latest

Abstract

   MoLE targets browser deployments, so Clients, Anchors, and Moderators
   need an HTTP transport for the protocol flows defined by the
   architecture.

   This document defines the Mole HTTP authentication scheme, which
   carries challenges and presentations for the endorsement and
   credential flows, and the headers used to return credential material.
   The grant exchanges with the Anchor are defined per protocol in
   [PROTOCOLS].

1.  Introduction

   [PROTOCOLS] defines the MoLE messages.  This document carries them
   over HTTP.  Challenges and presentations use the Mole authentication
   scheme [HTTP].  Credential material returns in the Mole-Credential
   response header.  Grant exchanges with an Anchor are HTTP POST
   requests defined in [PROTOCOLS].

2.  Conventions and Definitions

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and
   "OPTIONAL" in this document are to be interpreted as described in
   BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all
   capitals, as shown here.

   Message structures, their encoding, and the abstract operations
   (ProcessPresentation) are those of [PROTOCOLS].  Every binary value
   in a header is the unpadded base64url encoding ([BASE64]) of the TLS
   presentation encoding of the named structure.

3.  The Mole Authentication Scheme

   +--------+                                +-----------+
   | Client |                                | Moderator |
   +---+----+                                +-----+-----+
       |                                           |
       |<--- WWW-Authenticate: Mole challenge= ----+
       |                                           |
   (Redeem & Issue, if needed)                     |
       |                                           |
       +--- Authorization: Mole presentation= ---->|
       |                                           |
       |<-------------- Mole-Credential: update= --+
       |                                           |

   Each Mole challenge carries exactly one of these payload parameters:

      +===========+===========+====================================+
      | Parameter | Sent by   | Value                              |
      +===========+===========+====================================+
      | endorse   | Anchor    | EndorsementChallenge (Section 6.1) |
      +-----------+-----------+------------------------------------+
      | redeem    | Moderator | ModeratorChallenge                 |
      +-----------+-----------+------------------------------------+
      | challenge | Moderator | CredentialChallenge                |
      +-----------+-----------+------------------------------------+

                      Table 1: Challenge parameters

   The parameter name tells the Client which structure it holds;
   ModeratorChallenge and CredentialChallenge share a layout.  A server
   offering a choice sends several Mole challenges.  The Client picks
   one it supports and MUST ignore challenges of unknown type.

   A Mole credential in Authorization carries exactly one of these
   payload parameters:

         +====================+==================================+
         | Parameter          | Value                            |
         +====================+==================================+
         | credential-request | CredentialRequest                |
         +--------------------+----------------------------------+
         | presentation       | CredentialPresentation           |
         +--------------------+----------------------------------+
         | recovery           | CredentialRecovery (Section 6.4) |
         +--------------------+----------------------------------+

                     Table 2: Authorization parameters

   Parameters follow the auth-param syntax of Section 11.2 of [HTTP]; a
   value may be a token or a quoted-string.  One WWW-Authenticate field
   can carry several challenges (Section 11.6.1 of [HTTP]), and the
   rules below apply to each Mole challenge or credential separately.  A
   recipient ignores unknown parameters, including realm.  It MUST
   reject as malformed a challenge or credential with a repeated
   parameter, or with none or more than one of the payload parameters
   above.  It MUST reject a payload value that is not canonical unpadded
   base64url, or whose decoded value does not parse as the named
   structure.  A Client ignores a malformed challenge and can use
   another one.

4.  The Mole-Credential Field

   Mole-Credential returns credential material to the Client.  Its value
   is one parameter, with the syntax above:

                +===========+============================+
                | Parameter | Value                      |
                +===========+============================+
                | response  | CredentialResponse         |
                +-----------+----------------------------+
                | update    | optional<CredentialUpdate> |
                +-----------+----------------------------+

                   Table 3: Mole-Credential parameters

   An absent CredentialUpdate means the Moderator consumed the
   Credential without replacement.  A missing Mole-Credential field
   carries no such decision.  A Client MUST process Mole-Credential
   whatever the response status.

   A server sending Mole-Credential MUST also send Cache-Control: no-
   store.  A server answering cross-origin requests MUST list WWW-
   Authenticate and Mole-Credential in Access-Control-Expose-Headers.

5.  Configuration

   The Anchor and Moderator configurations are defined in [PROTOCOLS].
   A Client stores each Credential with the Moderator and Redeem & Issue
   endpoint it came from.  A Client that keeps a presentation for
   recovery also keeps the HTTP request that carried it.

6.  Exchanges

6.1.  Grant

   An Anchor that requires an Endorsement sends:

   struct {
     uint16 endorsement_type;
     opaque anchor_context<V>;
   } EndorsementChallenge;

   WWW-Authenticate: Mole endorse="<endorsement-challenge>"

   anchor_context is opaque to the Client.  An endorsement type that
   uses it defines how.  For the types of [PROTOCOLS] it is empty.  The
   criteria for granting are the Anchor's.  The grant requests are those
   of the endorsement type in [PROTOCOLS].

6.2.  Redeem & Issue

   The Moderator challenges with redeem:

   WWW-Authenticate: Mole redeem="<moderator-challenge>"

   The Client answers with a POST to the Redeem & Issue endpoint from
   configuration, whichever resource sent the challenge:

   Authorization: Mole credential-request="<credential-request>"

   On success the Moderator answers 200 with:

   Mole-Credential: response="<credential-response>"

6.3.  Presentation

   The Moderator challenges with challenge:

   WWW-Authenticate: Mole challenge="<credential-challenge>"

   A challenge in a 401 response means the resource requires a
   presentation.  A challenge in a 200 response means a presentation is
   optional, for instance to raise a limit.  Clients then apply the
   greasing rules of [PROTOCOLS].

   The Client repeats the protected request with:

   Authorization: Mole presentation="<credential-presentation>"

   The Moderator runs ProcessPresentation.  Every response to an
   accepted presentation, fresh or not, MUST carry the recorded update,
   including when the protected operation fails with a 4xx or 5xx
   status:

   Mole-Credential: update="<optional-credential-update>"

   For a fresh result the Moderator attempts the protected operation and
   returns its status.  For a result that is not fresh, it MUST return
   409 (Section 15.5.10 of [HTTP]) and MUST NOT attempt the protected
   operation.  A rejected presentation MUST NOT carry Mole-Credential.

   A Client that receives no Mole-Credential after sending a
   presentation keeps its pending state and MAY recover (Section 6.4).

   Each credential type MUST define the challenge fields that partition
   cached Credentials, or state that its Credentials are not cacheable.

6.4.  Recovery

   Instead of resending a presentation, a Client MAY send a POST with
   empty content to the Redeem & Issue endpoint:

   struct {
     uint16 credential_type;
     opaque recovery_handle<V>;
   } CredentialRecovery;

   Authorization: Mole recovery="<credential-recovery>"

   The recovery handle is defined by the credential type in [PROTOCOLS].
   The Moderator treats it as the byte-identical presentation and uses
   no other Client identifier.  It answers 409 with the recorded update
   if a result is still retained, and 401 otherwise, whether or not a
   record exists.  It MUST NOT perform the protected operation or verify
   a proof.

6.5.  Status Codes

     +========================+====================+=================+
     | Outcome                | Status             | Mole-Credential |
     +========================+====================+=================+
     | Malformed request      | 400                | none            |
     +------------------------+--------------------+-----------------+
     | Missing, expired, or   | 401                | none            |
     | invalid authentication |                    |                 |
     +------------------------+--------------------+-----------------+
     | Rejected by policy     | 403                | none            |
     | before acceptance      |                    |                 |
     +------------------------+--------------------+-----------------+
     | Credential issued      | 200                | response        |
     +------------------------+--------------------+-----------------+
     | Fresh accepted         | protected          | update          |
     | presentation           | operation's status |                 |
     +------------------------+--------------------+-----------------+
     | Accepted presentation, | 409                | update          |
     | not fresh, or recovery |                    |                 |
     +------------------------+--------------------+-----------------+

                          Table 4: Mole responses

   The Moderator MUST use these rules for every credential type.  A 401
   response MUST carry a Mole challenge for the required exchange.  A
   403 returned by the protected operation after a fresh acceptance is
   that operation's status, and carries the update.
