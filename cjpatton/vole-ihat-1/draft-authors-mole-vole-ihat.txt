                                Moussaka
                  draft-authors-mole-vole-ihat-latest

Abstract

   This document specifies Moussaka, a candidate post-quantum variant of
   the Issuer-Hiding Anonymous Token (IHAT) protocol.  Moussaka is based
   on the UOV digital signature scheme and the VOLE-in-the-Head proof
   system (a component of the FAEST signature scheme).  The anchor
   issues a token by signing a commitment to the client's state; to
   redeem a token, the client proves knowledge of the opening of this
   commitment and a signature produced by some anchor trusted by the
   moderator.  The commitment is instantiated with Keccak-p[800,12].

1.  Introduction

      WARNING This document specifies a cryptographic protocol that has
      not yet undergone significant security analysis.  It's not yet
      suitable for real world applications.  Implement at your own risk.

   The Issuer-Hiding Anonymous Token [IHAT] protocol allows a Client to
   redeem a token with a Moderator without revealing the identify of the
   Anchor that issued it.  Instead, the client proves the token was
   issued by some Anchor in the Anchor Set trusted by the Moderator.
   IHAT is also designed to be post-issuance unlinkable, meaning the
   issuance of a token cannot be linked to its redemption.

   IHAT meets these privacy goals unconditionally, meaning regardless of
   its computational resources, no attacker can learn which Anchor
   issued a token or to which Client it was issued.  On the other hand,
   it is well known that a quantum attacker can forge tokens by
   recovering the Anchor's secret key from its public key.

   This document specifies Moussaka, a variant of IHAT that is plausibly
   fully post-quantum.  Its design is based on the PoMFRIT blind
   signature scheme [PoMFRIT], which combines a post-quantum signature
   with a suitable zero-knowledge proof system and commitment scheme.
   The signer signs a commitment to the message, and the verifier checks
   a zero-knowledge proof-of-knowledge of the signature and the opening
   of the commitment.  Moussaka extends this paradigm in the natural
   way: instead of proving knowledge of a signature under the public key
   of a particular Anchor, the Client proves knowledge of a signature
   under some public key in the Anchor Set.

   Moussaka has significantly higher bandwidth cost compared to IHAT:

   1.  each Anchor public key is 42.6 kilobytes;

   2.  TODO kilobytes are transmitted during issuance; and

   3.  TODO*L kilobytes are transmitted during redemption,

   where L is the size of the Anchor Set. In particular, the size of the
   redemption proof scales linearily with the number of Anchors.

      NOTE(tnyuzg) We should be able to make redemption sublinear using
      the OR proof of ia,cr/2025/113, Section 4.1.

   On the other hand, Moussaka is round optimal: only two moves are
   required for issuance, whereas IHAT requires three.

   The remainder of this document is structured as follows.  Section 2
   defines some conventions and notation.  Section 3 provides a high-
   level overview of the protocol.  Section 4 defines the relevant
   interfaces for the signature scheme, commitment scheme, and proof
   system used by Moussaka and provides normative references for their
   specifications.  Section 5 specifies the protocol in full detail.
   Finally, Section 6 enumerates some security considerations for
   implementers and adopters.

3.  Overview

   Moussaka makes use of three cryptographic primitives:

   1.  The Unbalanced Oil and Vinegar [UOV] digital signature scheme.
       Each Anchor uses a UOV secret key to issue tokens, and during
       redemption, the Client and Moderator construct a sequence of UOV
       public keys to use as the Anchor Set.

   2.  The VOLE-in-the-Head (VOLEitH) zero-knowledge proof system, a
       component of the FAEST digital signature scheme [FAEST].

   3.  A commitment scheme based on the Keccak permutation [FIPS202].

   A UOV public key is a map P from F_q^n to F_q^m.  A UOV signature is
   a solution s to an equation P(s) = t, where t is called the target
   and is computed by hashing the message to be signed.  The UOV secret
   key is a trapdoor for P that can be used to efficiently sample
   signatures for a given target.

   The issuance protocol resembles blind signature issuance for blind
   RSA [RFC9474]:

   1.  The Client transforms the message it wants signed into a blinded
       message.  In our case, the blinded message is a commitment to the
       message, and the message consists of a nullifier and the intended
       redemption context ctx_red [IHAT].  The Client sends this
       commitment Com(nf, ctx_red, r) to the Anchor, where r is the
       opening of the commitment.

   2.  Instead of signing the commitment directly, the Anchor constructs
       a target t = Tag(Com(nf, ctx_red, r), ctx_iss) from the
       commitment and the issuance context ctx_iss [IHAT] and uses its
       trapdoor for the public key P to sample a solution s to P(s) = t.
       The Anchor then sends the signature s to the Client.

   3.  Lastly, the Client finalizes issuance by constructing t and
       checking that P(s) = t.

   The key difference between this protocol and blind RSA is that the
   Anchor observes the signature s in plaintext.  To ensure
   unlinkability, the Client must hide the signature from the Moderator
   during redemption.

   Let P[1], ..., P[L] denote the Anchor Set. To redeem a token, the
   Client presents the nullifier in plaintext along with a VOLEitH
   proof-of-knowledge of s, r for which P[i](s) = t for some i in [L]
   without revealing i.  In order to prove this statement with VOLEitH,
   we need to express it as an arithmetic circuit.

   Our arithmetization exploits the simple structure of UOV signatures.
   Namely, for any public P it holds that P(0^n) = 0^m.  The idea is to
   extend the witness s into z[1], ..., z[L] for which z[j] = s if j = i
   and 0^n otherwise.  The circuit evaluates the following equation:

     P[1](z[1]) + ... + P[L](z[L]) = Tag(Com(nf, ctx_red, r), ctx_iss)

      TODO Decide if this circuit is sound.  It seems too simple to
      work, but if a client could find a malformed z vector, it seems
      like they'd be able to forge signatures for one of the Anchor
      public keys.

   The commitment Com() is instantiated with a single evaluation of the
   Keccak-p[800,12] permutation [FIPS202].  Similar to TurboSHAKE
   [RFC9474], this parameterization of Keccak has half the number of
   rounds as used in SHA-3.  However, its state is also half the size of
   either SHA-3 or TurboSHAKE.  This helps reduce the size of the
   VOLEitH proof without significantly impacting the binding or hiding
   of the commitment.  See Section 6 for details.

   The Tag() function does not involve a hash at all.  Instead, it
   computes the target by simply encoding the commitment and issuance
   context into vectors over F_q and concatenating them together.  As a
   result, our scheme fixes the length of the issuance context to TODO
   bytes.  Likewise, we choose TODO bytes as the length for the
   nullifier and TODO bytes as the length of the presentation context in
   order to fit these values into Keccak-p[800,12].
