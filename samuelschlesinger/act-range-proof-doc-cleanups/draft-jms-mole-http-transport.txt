                          MoLE HTTP Transport
                  draft-jms-mole-http-transport-latest

Abstract

   MoLE targets browser deployments, so Clients, Anchors, and Moderators
   need an HTTP transport for the protocol flows defined by the
   architecture.

   This document defines the Mole HTTP authentication scheme, which
   carries challenges and presentations for the endorsement and
   credential flows, and the headers used to return credential material.
   The grant exchanges with the Anchor are defined per protocol in
   [PROTOCOLS].

1.  Introduction

   [PROTOCOLS] defines the MoLE messages.  This document carries them
   over HTTP.  Challenges and presentations use the Mole authentication
   scheme [HTTP].  Credential material returns in the Mole-Credential
   response header.  Grant exchanges with an Anchor are HTTP POST
   requests defined in [PROTOCOLS].

2.  Conventions and Definitions

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and
   "OPTIONAL" in this document are to be interpreted as described in
   BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all
   capitals, as shown here.

   Payload encodings and abstract operations are defined by [PROTOCOLS].
   Header payloads use canonical unpadded base64url ([BASE64]).  HTTP
   carries type-specific payloads directly, without outer type or length
   wrappers.

3.  The Mole Authentication Scheme

   +--------+                                +-----------+
   | Client |                                | Moderator |
   +---+----+                                +-----+-----+
       |                                           |
       |<--- WWW-Authenticate: Mole challenge-T= --+
       |                                           |
   (Redeem & Issue, if needed)                     |
       |                                           |
       +--- Authorization: Mole presentation-T= -->|
       |                                           |
       |<------------ Mole-Credential: update-T= --+
       |                                           |

   Payload parameter names end in -T, where T is a registered
   endorsement or credential type from [PROTOCOLS], written as exactly
   four lowercase hexadecimal digits.  For example, Rollatini
   (endorsement type 0x0002) is challenged with redeem-0002, and ACT
   (credential type 0x0001) is presented with presentation-0001.
   Recipients also accept uppercase digits, since parameter names are
   case-insensitive (Section 11.2 of [HTTP]).  Type 0x0000 is invalid.

   Each Mole challenge has exactly one payload parameter:

           +=============+=============+=======================+
           | Parameter   | Registry    | Decoded payload       |
           +=============+=============+=======================+
           | endorse-T   | Endorsement | Anchor context, empty |
           |             |             | for the types here    |
           +-------------+-------------+-----------------------+
           | redeem-T    | Endorsement | RedemptionChallenge   |
           +-------------+-------------+-----------------------+
           | challenge-T | Credential  | Type-specific         |
           |             |             | Challenge             |
           +-------------+-------------+-----------------------+

                       Table 1: Challenge parameters

   A server offers a choice using separate Mole challenges.  The Client
   ignores unknown types and chooses a supported configuration.  A
   redeem-T challenge selects the endorsement type.  The Client selects
   the credential type from the same Moderator's configuration,
   independently of the endorsement type.

   A Mole credential in Authorization selects one operation:

     +================================+=============================+
     | Parameters                     | Decoded payloads            |
     +================================+=============================+
     | redeem-E, credential-request-C | Redemption, IssuanceRequest |
     +--------------------------------+-----------------------------+
     | presentation-T                 | PresentationAndUpdate       |
     +--------------------------------+-----------------------------+
     | recovery-T                     | Recovery handle             |
     +--------------------------------+-----------------------------+

                    Table 2: Authorization parameters

   E uses the endorsement registry.  C, presentation, and recovery use
   the credential registry.  Only Redeem & Issue has two payload
   parameters.  It requires exactly one of each, in either order.  Type
   0001's empty redemption is carried as redeem-0001="".

   Parameters use auth-param syntax (Section 11.2 of [HTTP]).  Values
   can be tokens or quoted-strings.  Senders quote empty values.
   Recipients unescape quoted-strings before decoding.  Multiple
   challenges in one field follow Section 11.6.1 of [HTTP].  These rules
   apply to each challenge separately.  Unknown parameters, including
   realm, are ignored.  A name beginning with one of the operation
   prefixes above but lacking exactly four hexadecimal digits is
   malformed, not an unknown extension.  A recipient MUST reject
   duplicate parameter names, mixed operations, and missing or extra
   payload parameters, including payloads of unknown types.  It MUST
   reject noncanonical base64url and, for known types, trailing bytes or
   malformed content.  Clients ignore malformed challenges and may use
   another one.

   An unknown presentation type is treated as absent when authentication
   is optional and rejected when required, as specified by [PROTOCOLS].
   Other requests of unknown type are rejected.  Unknown types never
   select a known payload decoder.  Greased types follow these same
   rules.

4.  The Mole-Credential Field

   Mole-Credential returns credential material to the Client.  Its value
   is one parameter, with the syntax above:

          +============+========================================+
          | Parameter  | Decoded payload                        |
          +============+========================================+
          | response-T | IssuanceResponse                       |
          +------------+----------------------------------------+
          | update-T   | Update, or empty for recorded NoUpdate |
          +------------+----------------------------------------+

                    Table 3: Mole-Credential parameters

   T uses the credential registry and MUST match the pending exchange.
   The field contains exactly one parameter and MUST NOT be repeated.
   An empty update-T="" means the Moderator consumed the Credential
   without replacement.  A nonempty value carries the type's Update.
   Registered credential protocols MUST define nonempty Update
   encodings.  A missing Mole-Credential field carries no such decision.
   A Client MUST process Mole-Credential whatever the response status.
   The credential result does not establish whether the protected
   operation completed.  Recovery returns this result without another
   operation attempt.

   A server sending Mole-Credential MUST also send Cache-Control: no-
   store.  A server answering cross-origin requests MUST list WWW-
   Authenticate and Mole-Credential in Access-Control-Expose-Headers.

5.  Configuration

   The Anchor and Moderator configurations are defined in [PROTOCOLS].
   A Client stores each Credential with the Moderator and Redeem & Issue
   endpoint it came from.  A Client that keeps a presentation for
   recovery also keeps the HTTP request that carried it.

6.  Exchanges

6.1.  Grant

   WWW-Authenticate: Mole endorse-0002=""

   The grant endpoint comes from Anchor configuration.  The Client sends
   a POST with the type-specific grant message as its body.  The media
   type is application/mole-endorsement-request with a required type
   parameter using the same four-digit hexadecimal encoding.  The
   response uses application/mole-endorsement-response with the same
   type.  The Client MUST reject a mismatched type.  There is no outer
   EndorsementRequest or EndorsementResponse wrapper.  The first
   Rollatini request has empty content:

   Content-Type: application/mole-endorsement-request; type=0002

   The criteria for granting are the Anchor's.

6.2.  Redeem & Issue

   The Moderator challenges with the endorsement type:

   WWW-Authenticate: Mole redeem-0002="<redemption-challenge>"

   The Client answers with a POST to the Redeem & Issue endpoint from
   configuration, whichever resource sent the challenge:

   Authorization: Mole redeem-0002="<redemption>",
                       credential-request-0001="<issuance-request>"

   On success the Moderator answers 200 with:

   Mole-Credential: response-0001="<issuance-response>"

6.3.  Presentation

   The Moderator challenges with the credential type:

   WWW-Authenticate: Mole challenge-0001="<act-challenge>"

   A challenge in a 401 response means the resource requires a
   presentation.  A challenge in a 200 response means a presentation is
   optional, for instance to raise a limit.  Clients then apply the
   greasing rules of [PROTOCOLS].

   The Client repeats the protected request with:

   Authorization: Mole presentation-0001="<presentation-and-update>"

   The Moderator runs ProcessPresentation.  Every response to an
   accepted presentation, fresh or not, MUST carry the recorded update,
   including when the protected operation fails with a 4xx or 5xx
   status:

   Mole-Credential: update-0001="<update>"

   For a fresh result the Moderator attempts the protected operation and
   returns its status.  For a result that is not fresh, it MUST return
   409 (Section 15.5.10 of [HTTP]) and MUST NOT attempt the protected
   operation.  A rejected presentation MUST NOT carry Mole-Credential.

   A Client that receives no Mole-Credential after sending a
   presentation keeps its pending state and MAY recover (Section 6.4).

   Each credential type MUST define the challenge fields that partition
   cached Credentials, or state that its Credentials are not cacheable.

6.4.  Recovery

   Instead of resending a presentation, a Client MAY send a POST with
   empty content to the Redeem & Issue endpoint it stored with the
   Credential:

   Authorization: Mole recovery-0001="<recovery-handle>"

   The recovery handle is defined by the credential type in [PROTOCOLS].
   The Moderator treats it as the byte-identical presentation and uses
   no other Client identifier.  It MUST NOT verify a proof or attempt
   the protected operation.  If a result is still retained, it answers
   200 with the recorded update-T, including the empty value for a
   recorded NoUpdate.  Otherwise it answers 404 without Mole-Credential,
   whether or not a record exists.

6.5.  Status Codes

   +===========================+====================+=================+
   | Outcome                   | Status             | Mole-Credential |
   +===========================+====================+=================+
   | Malformed request         | 400                | none            |
   +---------------------------+--------------------+-----------------+
   | Missing, expired, or      | 401                | none            |
   | invalid authentication    |                    |                 |
   +---------------------------+--------------------+-----------------+
   | Rejected by policy before | 403                | none            |
   | acceptance                |                    |                 |
   +---------------------------+--------------------+-----------------+
   | Credential issued         | 200                | response-T      |
   +---------------------------+--------------------+-----------------+
   | Fresh accepted            | protected          | update-T        |
   | presentation              | operation's status |                 |
   +---------------------------+--------------------+-----------------+
   | Duplicate presentation    | 409                | update-T        |
   | with retained result sent |                    |                 |
   | to the protected resource |                    |                 |
   +---------------------------+--------------------+-----------------+
   | Recovery, result retained | 200                | update-T        |
   +---------------------------+--------------------+-----------------+
   | Recovery, result          | 404                | none            |
   | unavailable               |                    |                 |
   +---------------------------+--------------------+-----------------+

                         Table 4: Mole responses

   The Moderator MUST use these rules for every credential type.  A 401
   response MUST carry a Mole challenge for the required exchange.  A
   403 returned by the protected operation after a fresh acceptance is
   that operation's status, and carries the update.

   A Client MUST NOT infer chain termination from any status without the
   recorded empty update.
